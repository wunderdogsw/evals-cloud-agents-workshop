Pitfalls

Ambiguous task

Two experts would agree on pass or fail

Rigid grader

"96.12" rejected for 96.124991…

Shared state

Leftover files inflate scores between runs

Unread transcripts

Read them. Every failure, every time.

42%→95%

Opus 4.5 on CORE-Bench. Same model: only the eval was fixed (grader, task specs, setup).

When not to use evals

An eval takes work up front and pays you back later.

Few uses, early days

A skill you run a handful of times may never pay back. Using it yourself and checking by hand gets you far.

No definition of good

Can't describe a good result yet? Write a few cases by hand first. That makes you decide.

Only the easy cases

Tasks picked because they're easy to make or grade don't measure what matters.

Too subjective to check

If nobody can check that the grader is right, use human review instead.

Never as the only signal: use evals together with monitoring, user feedback and real conversations

When hillclimbing pays off

Raising a score only helps when it can still go up, and you can see why it moved.

Room to improve · the score is well below ~95%. Above that, work on cost or speed instead.
Bigger than the noise · the gain you want is bigger than the difference between runs.
One cheap change, one clear result · the score moves because of that change.
Skills are a good fit. Whether a skill loads depends on its description, the one thing you edit.
No room to improve, or too much noise → stop
